# Context Resilience — LAW 7 Implementation

LAW 7 states: "System MUST be resumable from STATE.md + TREE-STATE.json alone. All context lives in files, never in chat history." This document describes the three mechanisms that implement LAW 7, the four recovery paths they enable, and the design principle that governs them all.

---

## The Problem

The context window is volatile. It gets erased on session end, truncated on compaction, and corrupted by long conversations. Any information that exists only in the context window will be lost. This is not a risk — it is a certainty.

The research process spans multiple sessions, sometimes dozens. Claims take cycles to mature. Patterns emerge over weeks. A system that forgets between sessions is not doing research — it is repeatedly starting over.

---

## Three Mechanisms

### Mechanism 1: File-Based State (Always Available)

The most robust layer. Two files on disk, readable by any agent at any time, with no dependencies on databases or services.

#### STATE.md

**Location:** `.vibe-science/STATE.md`

**Contents:** A snapshot of the current research state, rewritten each cycle. Maximum 100 lines. Structured as:

```markdown
# STATE — [RQ-XXX] [Title]

**Stage:** T3 | **Cycle:** 14 | **Session:** a1b2c3d4
**Last updated:** 2026-01-20T10:30:00Z

## Active Claims
- C-003: Batch-corrected DE signature (confidence: 0.40, status: CONFOUNDED)
- C-007: Sex-differential response (confidence: 0.45, status: CREATED)
- C-009: Temporal dynamics in replication (confidence: 0.55, status: CREATED)

## Pending Gates
- DQ2 for C-003 (awaiting re-analysis with normalized counts)
- L-1 for C-009 (literature search pending)

## Recent Decisions
- C-003 downgraded from 0.65 to 0.40 after propensity matching (cycle 12)
- Branch T3-explore-4 completed: partial replication found (cycle 15)

## Open Questions
1. Is library size confounded with treatment group?
2. Temporal dynamics — real or artifact?

## Next Steps
1. Re-run C-003 DE with library-size normalization
2. Literature search for temporal dynamics of perturbation signatures
```

**Update frequency:** Every cycle (THINK-EXECUTE-EVALUATE-CRYSTALLIZE), the CRYSTALLIZE phase rewrites STATE.md. Not appended — rewritten entirely. This keeps it current and within the 100-line limit.

**Why 100 lines:** This is approximately 1,500-2,000 tokens. Small enough to inject into any context without significant cost, large enough to capture the essential state.

#### TREE-STATE.json

**Location:** `.vibe-science/TREE-STATE.json`

**Contents:** Full serialization of the research tree. Every node, every branch, every status. This is the complete structural record of what was explored, what was promoted, what was killed.

**Update frequency:** Every time a tree operation occurs (branch, promote, kill, merge).

**Size:** Unbounded, but typically 5-50KB for active research projects.

**Why JSON:** Machine-readable. Can be loaded, queried, and validated programmatically. STATE.md is for humans; TREE-STATE.json is for machines.

### Mechanism 2: PreCompact DB Snapshots

**Trigger:** The PreCompact hook fires immediately before context compaction.

**What it captures:**

1. **Active claims** — All claims with status CREATED (not yet KILLED, DISPUTED, or R2_REVIEWED). Includes claim ID, description, confidence, and current evidence chain.
2. **Pending serendipity seeds** — Seeds that have been flagged but not yet followed up. Includes seed ID, description, and score.
3. **Spine entry count** — Total number of research spine entries in the current session. Indicates how much work was done before compaction.
4. **STATE.md content** — The full text of STATE.md at the time of compaction, truncated to 10KB if necessary.

**Storage:** Saved as a spine entry with type `COMPACT_SNAPSHOT` in the database. Queryable by session ID and timestamp.

**Why this matters:** Context compaction is the most common cause of information loss. The agent is mid-thought, the context fills up, and everything before the compaction boundary is summarized or discarded. The PreCompact snapshot ensures that the critical state is preserved in the DB, even if the context summary is lossy.

**Limitations:** The snapshot is only as good as the DB. If the DB is unavailable, the snapshot is not created. This is why Mechanism 1 (file-based state) exists as a fallback.

---

### Mechanism 3: Progressive Context Building

**Trigger:** The SessionStart hook fires at the beginning of every session.

**What it loads from the DB:**

1. **Last session summary** — The narrative summary generated by the Stop hook of the previous session. Provides a human-readable account of what happened, what was decided, and what comes next.
2. **Observer alerts** — Any unresolved warnings from the Observer (stale files, desync, orphaned data). These persist across sessions until resolved.
3. **R2 calibration hints** — Temporal-decay-weighted summary of R2's historical weaknesses and SFI performance (see `r2-calibration.md`). Guides R2's focus areas.
4. **Cross-session patterns** — Active patterns from the `research_patterns` table (see `pattern-extraction.md`). Highlights recurring issues and learned behaviors.
5. **Pending serendipity seeds** — Seeds from previous sessions that were never followed up. These represent unexplored opportunities.

**Injection:** The assembled context is returned via `hookSpecificOutput.additionalContext`, injected into the agent's context at session start. The total injection is approximately 700 tokens — enough to provide meaningful continuity without consuming significant context budget.

**Why 700 tokens:** This is a budget chosen through empirical testing. Below 500 tokens, critical information is lost. Above 1,000 tokens, the injection competes with the user's actual prompt. 700 tokens provides the best balance.

## Four Recovery Paths

Different failure modes trigger different recovery paths. The system is designed to recover from any single point of failure, and to degrade gracefully under compound failures.

### Path 1: Fresh Session (Normal)

**Scenario:** A new session starts after the previous session ended normally.

**Recovery chain:**
1. SessionStart hook fires.
2. Opens DB, queries last session summary, observer alerts, R2 calibration, patterns, pending seeds.
3. Builds ~700-token context block.
4. Injects into agent context.
5. Agent has full continuity.

**What is available:** Everything. DB has the narrative summary, spine entries, embeddings, patterns. Files have STATE.md and TREE-STATE.json.

### Path 2: Post-Compaction (Mid-Session)

**Scenario:** Context compaction occurred during a session. The agent's context window has been truncated.

**Recovery chain:**
1. PreCompact hook fired before compaction, saving a COMPACT_SNAPSHOT to the DB.
2. After compaction, the agent's reduced context includes the compaction summary.
3. On the next prompt, UserPromptSubmit performs semantic recall, which may surface the COMPACT_SNAPSHOT.
4. SessionStart context (if still in the window) provides the broader session context.

**What is available:** DB has the COMPACT_SNAPSHOT (active claims, pending seeds, STATE.md content at compaction time). Files have the current STATE.md and TREE-STATE.json (which may have been updated since the snapshot).

### Path 3: Crash / No DB (Degraded)

**Scenario:** The DB is unavailable — deleted, corrupted, or `better-sqlite3` is not installed.

**Recovery chain:**
1. SessionStart hook detects missing DB. Logs a warning. Skips DB operations.
2. No progressive context is injected (no narrative summary, no calibration, no patterns).
3. Agent must rely on STATE.md and TREE-STATE.json on disk.
4. Manual resume: the user or agent reads STATE.md to understand current state, reads TREE-STATE.json to understand the research tree.

**What is available:** Only files. STATE.md provides the essential state (active claims, pending gates, next steps). TREE-STATE.json provides the tree structure. No narrative continuity, no patterns, no calibration.

**This is why LAW 7 requires that STATE.md + TREE-STATE.json be sufficient for resumption.** These two files are the ultimate fallback.

### Path 4: Cross-Session (Long-Term)

**Scenario:** Multiple sessions have passed. The agent needs to resume work started weeks ago.

**Recovery chain:**
1. SessionStart loads the most recent session summary from the DB. If multiple sessions intervened, it loads the latest one (which itself referenced the previous state).
2. Cross-session patterns persist in the DB. Patterns that were relevant weeks ago are still available (with decayed confidence).
3. Narrative summaries from intermediate sessions are available via semantic recall if the UserPromptSubmit hook queries for them.
4. STATE.md reflects the state at the end of the most recent session.

**What is available:** DB has all session summaries, patterns, and spine entries (with temporal decay applied to relevance scoring). Files have the latest STATE.md and TREE-STATE.json.

## Design Principle

> "The context window is a buffer that gets erased. The DB is persistent memory. The files are the source of truth."

This principle governs all resilience decisions:

1. **Never trust the context window.** It will be erased. Anything important must be written to a file or the DB before the current turn ends.
2. **Files are the ultimate fallback.** STATE.md and TREE-STATE.json must contain enough information to resume research with zero DB, zero context, and zero prior knowledge.
3. **The DB adds richness, not necessity.** Narrative summaries, patterns, calibration, and semantic recall make resumption smoother. But they are enhancements, not requirements.
4. **Redundancy is deliberate.** The same information exists in multiple places (context, DB, files) because each layer has different failure modes. This is not waste — it is resilience.

## What Must Be Written and When

| Information | Written To | When | By Whom |
|------------|-----------|------|---------|
| Current state | STATE.md | Every CRYSTALLIZE phase | Researcher |
| Tree structure | TREE-STATE.json | Every tree operation | Researcher |
| Session summary | DB (sessions table) | Stop hook | Stop hook |
| Active claims | DB (COMPACT_SNAPSHOT) | PreCompact hook | PreCompact hook |
| Patterns | DB (research_patterns) | Stop hook | Stop hook |
| Spine entries | DB (research_spine) | PostToolUse hook | PostToolUse hook |
| R2 reviews | DB (r2_reviews) | During review | R2 / Orchestrator |
| Serendipity seeds | SERENDIPITY.md + DB | On discovery | Serendipity scanner |

Every row in this table is a LAW 10 obligation: "If it's not in a file, it doesn't exist."

---

*This protocol implements LAW 7 across all failure modes. The three mechanisms provide layered resilience: files for worst-case, DB for normal operation, progressive context for seamless continuity.*
